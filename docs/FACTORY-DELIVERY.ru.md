# Доставка с заводским robotio: отдельный проверяемый допуск

Исполнитель `DeliveryRobot` поддерживает два существующих протокола. Native STM32 по-прежнему использует `load_settings()`/`seal_setup()` с source SHA и калибровкой контроллера. Factory micro-ROS robotio с `ManualArm.factory_timed=true` использует `src/factory_delivery.py`. Наличие заводского протокола больше не является безусловным запретом доставки, но оно не превращается в доказательство выполненной физической приёмки.

## Что исправлено

- `blockers()` проверяет реальные артефакты factory-сценария вместо постоянного сообщения «сценарий robotio не принят». `begin()` больше не обращается к отсутствующему native `arm.profile`.
- `permit()` сохраняет `missions.survey_permit(mid)` для владельца миссии, датчиков и навигации. Состояние руки factory проверяется отдельно по текущему boot и сохранённому record, поэтому движение базы не вызывает чужую проверку stationary arm commissioning. Во время пути руки остаётся HOLD базы и контроль исполнительной миссии.
- Factory-путь получает целочисленные конечные servo-команды, как требует протокол. Результат считается `command_completed`, `measured=false`, `attained=false`; рассчитанная поза не выдаётся за измеренную. Совпадающая с текущей командная цель проверяется по фазе, завершению и истечению runtime, без native `_state()`.
- Guarded closure сохраняет `final_deg`. Подъём, транспортная поза и размещение используют именно этот угол; они больше не дожимают предмет до `close_deg`. Решение визуальной проверки `stop` запрещает подъём. После раскрытия или завершения задания сохранённый угол удаляется.
- Конечная проверка visual alignment использует тот же TCP offset, что и три коррекции; ненулевой принятый offset больше не создаёт ложную ошибку несходимости.
- MoveIt/collision checking, поиск и RGB-D reacquisition, Nav2, визуальная проверка удержания и размещения остаются существующими. Во время движения руки допускается только свежая 2D association через `tracking_status()`; метрическая поза камеры должна дождаться завершённой команды. Неизвестный/потерянный предмет не считается удержанным.

## Требуемые существующие настройки

`load_factory_settings(root)` читает, но **не создаёт**:

1. `config/delivery.json`: проверенные поисковые/транспортные позы, направление TCP, плоскость пола, места поиска, корзина, область размещения, map_epoch и `place_poses`. `guarded_closure_enabled=true` требуется для factory-сценария.
2. `config/handeye-accepted.json`: принятая геометрия `arm4`, источник `joint_state_source=command_estimate`, ссылка и SHA исходного физического validation record.
3. `config/gripper-accepted.json`: измеренное раскрытие, допустимые open/sock-close, ссылка и SHA физического record.
4. Текущие `config/explorer.urdf`, `config/explorer.srdf`, `config/factory-arm-startup.json`, `config/arm-motion.json`.
5. `config/factory-delivery-acceptance.json`: только связи с уже выполненными отдельными проверками.

Manifest имеет `scope="factory_delivery_prerequisites"`, `controller_protocol="factory_micro_ros"`, `joint_state_source="command_estimate"`, текущий `map_epoch`, `places_sha256`, `artifacts` (пути → SHA256) и `physical_test_records` (пути → SHA256). Все настройки из списка проверяются по фактическому содержимому. Можно добавить дополнительные существующие файлы/сохранённый образ в `artifacts`; они тоже проверяются. Source SHA native STM32 не выдумывается для протокола, который не сообщает его. Сам manifest не доказательство полного цикла; `physical_delivery_verified=false`.

`places_digest(place_poses)` считает SHA канонического JSON именованных `[x,y,yaw]`. Это не хэш SQLite-файла с меняющимися timestamp. При `begin()` существующий `validated_places()` повторно проверяет эти координаты и текущую эпоху карты.

## Отдельные физические проверки

Каждый record содержит реальные время `at`, `kind`, `hardware_executed=true`, `simulation=false`, `operator_observed=true`, `outcome="passed"`, factory protocol/source pose, `artifacts` и независимые `observation_artifacts` (пути → SHA). Настройки и журнал нельзя выдать за наблюдение. Все перечисленные наблюдения должны существовать и совпадать по хэшу. Модуль не пишет такие records автоматически и не ставит commissioning flags.

Области `kind` и минимальные связи:

| Область | Что физически проверить | Настройки, к которым привязан record |
|---|---|---|
| `factory_arm` | Принятая исходная поза, короткий свободный путь/возврат и отмена без последующих команд | URDF/SRDF, startup и motion |
| `camera_geometry` | Координаты известных точек в нескольких завершённых позах руки, плоскость и доступная область подбора | hand-eye, URDF/SRDF, delivery; текущие map_epoch/places SHA |
| `gripper_contact` | Измеренное раскрытие, guarded контакт с носком, короткий подъём и сохранение предмета | gripper, hand-eye, URDF/SRDF и delivery |
| `localization` | Возврат в сохранённое место поиска и место корзины с проверкой позы/лидаров | delivery; текущие map_epoch/places SHA |

Таким образом проверка руки не требует прежней learned-policy статистики или отсутствующего MCU source SHA. Проверка локализации не требует раскрытия захвата. Но изменённые настройки, к которым относилась физическая попытка, инвалидируют её допуск. Полный ранее успешный delivery не требуется для первой контролируемой попытки: это отдельная проверка после допуска предпосылок.

## Интеграция и следующая проверка

Существующие web/`DeliveryTask` продолжают использовать `DeliveryRobot.blockers()/begin()`: отдельный интерфейс запуска не нужен. `next_exercises(root)` возвращает недостающие пути, четыре области проверки и конкретный следующий порядок действий. При отсутствующих артефактах робот не движется, а диагностика указывает именно отсутствующий файл. Ни конфигурации, ни принятые позы в этом изменении не созданы.

После настоящих отдельных проверок можно оформить hash-bound manifest и выполнить одну наблюдаемую попытку: поиск → навигация → осмотр → выравнивание → guarded grasp → визуально подтверждённое удержание → перевозка → поддержка/раскрытие → проверка размещения. Потеря зрения, новой локализации или boot останавливает зависимые стадии. Успех должен записываться существующим визуальным verifier; завершение команд само по себе не доставка.

Компьютерные проверки: `PYTHONPATH=src python3 -m unittest discover -s tests -p 'test*delivery*.py'`. Новые fixtures являются синтетическими contract records в временном каталоге: они доказывают совместимость загрузчика/исполнителя и отказ неправильных связей, не физическую приёмку нашего робота.

## Одна процедура фиксации результата

`bin/accept-factory-exercise.py` работает только с уже сохранёнными файлами. Он не открывает UART/камеру, не публикует ROS-команды, не калибрует и не создаёт позы. Для полных проверок используйте Python окружения Explorer с NumPy/OpenCV; команда `status` умеет сообщить отсутствующий manifest даже без NumPy.

```sh
cd ~/Explorer
python3 bin/accept-factory-exercise.py status
```

Перед физическим упражнением существующий исполнитель должен сохранить SHA используемых scoped настроек; после упражнения — его исходные результаты, кадры/RGB-D/сенсорные наблюдения и их SHA. Нельзя после старого теста просто добавить сегодняшние хэши и объявить его текущей проверкой. Именно поэтому исторический hand-eye result без привязки к текущим scoped настройкам не оформляется автоматически.

Исходный JSON имеет `kind="<scope>_exercise"`, реальное `at`, `hardware_executed=true`, `simulation=false`, `outcome="passed"`, factory protocol/command-estimate source, `artifacts`, `observation_artifacts`. Дополнительно он содержит содержательные данные:

- `factory_arm_exercise`: `start_deg`, `goal_deg` с реальным изменением, текущий `boot_id`, SHA полной траектории, число публикаций, завершение команды и проверку отсутствия новых публикаций после отмены. Визуальное подтверждение изменения даёт оператор; encoder attainment не заявляется.
- `camera_geometry_exercise`: `comparisons` минимум двух завершённых поз с `translation_error_m`/`rotation_error_deg` в проверенных пределах 18 мм/3°. Область, карта и именованные места привязаны к текущему delivery сценарию.
- `gripper_contact_exercise`: измеренные `open_aperture_mm`/`closed_gap_mm`, наблюдавшийся guarded контакт и реальные `before`/`after` кадры геометрии. `verify_lift()` запускается заново по этим данным; три наблюдения до/после, стабильная association, действительная геометрия камеры, подъём и удержание не меньше секунды обязательны. Время кадров связано со временем упражнения. Одна галочка «получилось» не заменяет verifier.
- `localization_exercise`: ошибки позиции/угла, независимые ошибки обоих лидаров и `places_checked` со всеми местами текущего сценария. Пределы — 15 см/10° и 8 см медианной разницы лидаров. Источник привязан к текущей эпохе/координатам мест.

После уже выполненного упражнения оператор отдельно подтверждает то, что действительно наблюдал:

```sh
python3 bin/accept-factory-exercise.py record \
  --scope factory_arm \
  --source data/physical-exercises/actual-arm-result.json \
  --observation data/physical-exercises/actual-arm-image.jpg \
  --observed --operator-result passed
```

Это пример путей, не готовые журналы. `--observation` можно повторить. Утилита проверяет существующие источники и связи, сохраняет операторскую аннотацию отдельно в `data/factory-delivery-exercises/` и возвращает её путь/SHA. Исходный журнал не изменяется. `--operator-result failed` сохраняет отрицательную аннотацию успешного командного теста, если оператор увидел проблему; такая запись не проходит допуск. Сам исходный провал физического verifier остаётся сохранённым первичным журналом и не может быть переименован в successful exercise.

Когда четыре отдельных упражнения действительно пройдены, сначала проверяется их совместимость:

```sh
python3 bin/accept-factory-exercise.py seal \
  --record data/factory-delivery-exercises/factory_arm-REAL.json \
  --record data/factory-delivery-exercises/camera_geometry-REAL.json \
  --record data/factory-delivery-exercises/gripper_contact-REAL.json \
  --record data/factory-delivery-exercises/localization-REAL.json
```

По умолчанию это dry-run, manifest не пишется. Добавление `--write-manifest` к той же команде сохраняет `config/factory-delivery-acceptance.json` **только после** повторной проверки всех файлов, scoped связей и содержательных исходных данных. Отсутствующая область, изменённый файл, устаревшая карта или один только `accepted=true` останавливают оформление. Чужой существующий manifest не перезаписывается; сначала нужно отдельно сохранить его. Этот допуск разрешает первую контролируемую попытку существующего `DeliveryTask`, а не утверждает, что доставка уже произошла.
